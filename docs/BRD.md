# **Business Requirements Document (BRD)**

**Project Title:** Administrative Workflow and Records Management Web Application

## **1. Purpose of the Project**

The purpose of this project is to develop a web-based system that will improve how the agency handles daily administrative tasks and records. The system aims to replace manual and scattered processes with a centralized platform that allows staff to efficiently manage tasks, store information, and access records when needed.

## **2. Project Overview**

The proposed system will serve as an internal tool for the agency to support administrative operations. It will provide an organized and user-friendly interface where users can log in, manage tasks, encode records, and view summarized information through a dashboard. The system focuses on improving productivity, reducing errors, and ensuring that important data is easily accessible.

## **3. Business Objectives**

The project aims to streamline administrative workflows, improve record organization, and enhance overall operational efficiency. It also seeks to minimize manual data handling, reduce the risk of lost or inconsistent records, and provide a simple digital solution that supports daily office activities.

## **4. Scope of the Project**

The system will include user login functionality, a dashboard for viewing summarized data, task management features, and a records management module. Users will be able to create, update, and view tasks, as well as encode and manage basic records. The system will also include search and filtering capabilities to help users quickly find information.

The project is limited to front-end development and basic system functionality. Advanced integrations, automation, and complex backend processes are not included in this scope.

## **5. Stakeholders**

The primary stakeholders include the agency staff who will use the system for daily operations and the project developer responsible for designing and implementing the application. Supervisors or administrators may also review and monitor system usage and outputs.

## **6. Functional Requirements**

The system must allow users to securely log in before accessing features. It must display a dashboard that provides an overview of tasks and records. Users should be able to create, edit, and view tasks within the system. The application must also allow users to input, update, and view records in an organized format. Additionally, the system should provide search and filtering functions to make data retrieval faster and more efficient.

## **7. Non-Functional Requirements**

The system should be easy to use, with a clean and simple interface suitable for non-technical users. It should load quickly and respond efficiently to user actions. The application must ensure basic data security by restricting access through login functionality. It should also be accessible through standard web browsers without requiring complex setup.

## **8. Tools and Technology Requirements**

The system will be developed using standard web technologies suitable for front-end development. The user interface will be built using HTML, CSS, and JavaScript to create responsive and interactive pages. A front-end framework such as Bootstrap may be used to simplify design and ensure a consistent layout.

For development and coding, a code editor such as Visual Studio Code will be used. Version control may be managed through Git to track changes and maintain project history. The application can be tested and accessed using common web browsers like Google Chrome.

If basic data storage is required for demonstration, lightweight options such as local storage or simple JSON files may be used instead of a full database system. The system is designed to run in a local development environment and does not require deployment to a live server.

## **9. User Roles and Responsibilities**

The system will have two primary user roles. The Administrator has full access to the system, including managing tasks, viewing all records, and monitoring overall activity. The Administrator can also update or modify records as needed. The Staff user has limited access and is mainly responsible for encoding data, updating assigned tasks, and viewing relevant records. This role-based access ensures proper control and organization within the system.

## **10. Project Timeline (Estimated for 492 Hours OJT)**

The project will be completed in phases to simulate actual development work. The first phase involves planning and requirements gathering, where the system features and structure are defined. The second phase focuses on designing the user interface, including layout, forms, and navigation flow. The third phase covers development, where the main pages such as login, dashboard, task management, and records module are created.

The fourth phase involves testing and revisions, ensuring that all features function properly and the interface is user-friendly. The final phase includes documentation and preparation of deliverables such as screenshots, reports, and system demonstration. Each phase is distributed across the total required training hours to reflect continuous progress and learning.

## **11. Acceptance Criteria**

The system will be considered acceptable once it meets the defined requirements. Users must be able to log in successfully and navigate the system without difficulty. The dashboard should display summarized information clearly. Task management features must allow creation, updating, and viewing of tasks. The records module should allow proper encoding and display of data.

Additionally, the system should respond smoothly to user interactions, and all pages must load without errors. The interface should be clear and easy to understand, even for non-technical users. Supporting documentation, including screenshots and basic usage explanation, must also be provided as part of the final output.

## **12. Assumptions**

It is assumed that users have basic knowledge of using a computer and web browser. The system will be used within a controlled environment and will not require external integrations. It is also assumed that the data entered into the system is managed and maintained by authorized users.

## **13. Constraints**

The project is limited by time and is expected to be completed within the required training duration. It focuses only on essential features and does not include advanced system capabilities. Technical resources and infrastructure are assumed to be minimal.

## **14. Expected Outcome**

The expected outcome is a functional prototype of a web-based administrative system that demonstrates how digital tools can support and improve office workflows. The system will showcase the ability to manage tasks and records in a structured and efficient manner, providing a practical solution for everyday administrative needs.
